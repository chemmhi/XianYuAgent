# 密码登录后业务安全验证未调度（2026-11-22）

## 实际问题与生产证据

腾讯云 `0854026` 的用户密码登录于 10:39:42 +08:00 成功，凭证 active，保存账密启用，IM 有持续新心跳。10:43:20 起，独立的 `mtop.taobao.idlemessage.pc.user.query` 4.0 请求产生 ACCOUNT_VALIDATION_REQUIRED，不能以登录成功或 IM 心跳证明此业务请求已通过验证。

本轮只读生产核对发现：该接口 15 条验证风险、96 条 MTOP_RETRY_EXHAUSTED 记录；后台验证调度、滑块处理事件均为零；accounts.verification_sessions 最新记录仍为 10 月 26 日。生产配置已开启浏览器验证、自动模式、远程手动模式和原生验证。因此两条路径没有真正进入验证码执行阶段，而不是已经各自尝试并失败。

已登记风险保存了完整只读契约：来源、版本 4.0、type/isOwner/sessionId/sessionType 参数。一次受控原请求重验中，实际 Cookie 与签名一致，平台返回 SUCCESS，没有新的 Set-Cookie；诊断未保存凭证、未核销风险。说明该业务风险当前可重验恢复，但调度被跳过后旧风险不能自行清理。96 次重试耗尽是独立错误记录，具体原因未确认，不能据此声称执行过验证码。

## 两条路径的共同根因

- XianyuImService.requestVerificationRecovery 在已保存凭证的 loginMethod=password_http 时直接 return；这条限制把登录后的业务恢复一并禁用了。
- 页面正式入口 POST /api/v1/verification-sessions/retry 经 VerificationRuntime.retry 回调相同调度器。接口可以返回 pending，实际却没有创建验证会话，页面无法取得画面。
- IM Token 的额外挑战分支也排除了 password_http。即使以后 Token 返回了合法挑战地址，仍不会进入既有恢复链路。

业务验证 profile 与密码设备 SDK profile 各自持久化，不能把两者称为同一设备上下文。原代码也没有把密码登录保存的 UA 传给业务验证浏览器；恢复后继续用旧 UA 发 HTTP，会造成会话身份不一致。

## 修复边界和用户行为

移除以上认证方式限制，使已登录的密码账号复用既有业务读恢复、IM Token 恢复和统一人工/自动验证协调器。密码提交及登录时的 HTTP/二维码验证仍由 PasswordLoginService 负责；此修复不调用密码重登、不自动重发消息或业务写操作。

后台先重验原来源；仍被阻断时才在原服务端浏览器里处理官方挑战。页面可接管同一会话的画面和输入。业务读风险要求原请求重验、目标身份和凭证 CAS/风险来源版本一致，不强制刷新健康 IM；IM 风险还须匹配 Token/deviceId、真实注册和新心跳。其他风险保持独立，协调器会区分本轮完成与仍有其他风险的部分恢复。

给验证浏览器增加仅内部使用的单次 UA 参数，密码账号业务读和 Token 两路均传经过现有校验的保存 UA；其他登录方式沿用原配置。去重键包含 UA，避免不同身份参数被错误合并。继续使用账号业务验证 profile、完整 Cookie 快照、共享 profile 锁，未复制或并用密码 SDK profile。权限、generation、deviceId、CAS、风险 revision 和手动展示 ACK 均保留。无数据库迁移和新依赖，无前端产品代码改动。
