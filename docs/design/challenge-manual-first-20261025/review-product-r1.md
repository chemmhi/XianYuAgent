# 人工优先挑战方案独立产品评审 R1

评审对象：`proposal.md` v0.1（2026-10-25）。
评审身份：独立审核者，未参与方案起草。
范围：业务和交互设计、5 秒人工优先、90 秒人工窗口、生命周期、入口一致性、用户审核及验收覆盖。
性质：**设计评审**。只读取设计和本地现有代码；没有编码、运行实现测试、连接生产或验证真实平台放行。下述建议不是实现已完成的证明。

## 结论

**FAIL，修订后复审。** 发现 0 项 P0、2 项 P1、4 项 P2。总体方向合理，已有较完整的互斥、身份复验、写操作不重放和预算边界；但超时交接与结果口径仍可使用户刚完成人工验证时又被自动操作，或者页面报告恢复而账号仍需验证。其余缺失会直接影响人工优先是否真的可用，建议在用户最终审核前补齐。

## PR-R1-001 — P1：人工交接屏障只处理输入，没有处理已提交但未返回的验证

位置：方案 §6 第 125–128、136 行；§12 第 213 行。

当前约定在人工 90 秒到期、用户交给系统、断网宽限到期时，释放鼠标和排空输入后立即进入自动。它没有定义人工作答已经发出、平台 verdict 尚未返回的中间状态。比如用户在第 89.9 秒松开滑块，平台 500 毫秒后返回成功；第 90 秒的超时任务已经使 `human_active → auto_active` 并运行 solver。输入互斥仍然成立，但系统可能在平台正在接受人工答案或导航交接时重新操作页面。当前状态表只写 `human_active → handoff` 的人工成功入口，也未写迟到 verdict 与切换任务的优先规则。

建议在所有人工退出原因中统一增加“答案处理中/交接判断”屏障：先禁止新输入并安全释放，再检查当前 generation 的 verdict、导航和已提交请求；有成功则优先 handoff，不运行 solver；尚在等待平台响应时进入有界观察状态，超过观察上限才按明确的失败/超时策略继续。若无法确认安全，停止本轮，不能假定 pointer-up 等于平台已处理完毕。请给出观察上限及是否计入 90 秒/300 秒的规则，不要求简单无限等待。

验收应新增：89.9 秒提交而 90.4 秒成功、手动点“交给系统”后成功回包、断网宽限结束后成功回包、成功 verdict 与 timeout 同时到达；每种只出现一次 handoff，自动手势次数为 0，迟到旧 generation 成功不能影响新挑战。

## PR-R1-002 — P1：写操作/未知来源的“验证完成”“会话成功”“账号恢复”没有可一致实现的口径

位置：方案 §4 第 82–83 行；§6 第 130、134 行；§11 第 199–203 行。

方案要求按来源核销，写操作不重放，这两点正确。但 §11 未说明只完成安全探针后的写来源如何呈现：它不能证明原发货/改价/发消息接口恢复，也未规定该来源风险应保留多久、什么后续证据才能核销、会话此时应 succeeded 还是某种部分完成。§4 的通用成功文案却是“账号连接已恢复”。存在同一账号的只读来源通过而写来源仍未核销的情况，此时用户会同时看到成功抽屉和“需要安全验证”，重现当前困惑。

代码证据：`apps/api/src/xianyu-verification-read-recovery.ts` 在 `!request` 的安全探针分支只记录 `verification_probe_completed` 然后 `continue`，不会 `clearAccountRisk`；原始只读请求复验成功才清对应风险。`xianyu-verification-request.ts` 将 IM 来源与中央只读白名单分开。设计应保留这些边界，不能用安全探针成功直接清写来源风险。

建议给出来源结果表：IM 已恢复、只读来源已恢复、写/未知来源安全探针通过但原操作待核对、仍失败来源。明确会话执行结束和账号总体风险的区别，部分结果显示“本次验证已完成，仍有 N 项待确认”，而非笼统报告账号恢复。再定义用户核对并重新提交原操作时，现有业务成功证据如何按 source/episode/revision 核销；没有可用安全证据的来源保持风险并明确后续路径。

验收应覆盖同账号混合 IM/read/write 来源、探针成功但原写来源仍受限、原写结果未知、用户核对后显式重试成功；断言提示、risk 和原写请求次数一致。

## PR-R1-003 — P2：直接拖动触发接管时，ACK 前已经松手的手势没有处理规则

位置：方案 §4 第 86 行；§7 第 146 行；验收 T03。

“按下请求接管，ACK 后才注入第一个 pointer-down”没有覆盖网络延迟期间的 pointer-up/cancel、失焦和弹窗关闭。用户在 200 毫秒内完成一次点击，接管 ACK 在 300 毫秒后到达，若此时仍注入保存的 down，就会发生远端孤立按下；若直接重放全部拖动轨迹，又与禁止迟到输入和新鲜画面规则冲突。当前 T03 只描述结果，没有规定这种常见慢网路径。

建议明确 ACK 前只保留候选 down 和当前本地指针状态，不向远端缓存重放整个手势；若 ACK 前已 up/cancel，ACK 到达后不注入 down，提示用户再次拖动，是否保留已获得的人工控制权也应确定。ACK 后仍按住的情况需规定 down 坐标、新鲜帧、pointer capture 和后续 move 起点，超过阈值要求重新按下亦可。对于“我来验证”按钮，接管成功后再作答最容易解释。

新增测试：ACK 前 up、cancel、失焦、手指离开、组件卸载及倒计时到期；断言零孤立 down、零自动重放历史轨迹，提示可理解。

## PR-R1-004 — P2：展示租约和多账号队列的公平性规则不足以支撑“人工优先 5 秒”承诺

位置：方案 §4 第 79、90 行；§5 第 99–110 行；§8 第 158 行；§9 第 172、181 行。

文档规定唯一画面消费者和“有界展示租约”，但没有给租约时长、续约条件、候选冲突仲裁或优先窗口中展示页消失后另一个前台页是否可接替的规则。另一个账号正在人工处理时，队列中的新挑战会在 8 秒后自动执行；这意味着用户虽在线且希望手动，也可能一次都没看见该挑战。该取舍可以接受，但不能只在技术队列描述中隐含，用户审核决策第 1 条并未指出多账号繁忙时也会跳过人工机会。

建议明确：同一 subject 的候选排序和租约到期；优先窗口换展示页沿用原 deadline；人工接管页与展示租约的关系；队列点击可否主动切换/接管而不干扰原会话；资源繁忙与展示繁忙各自适用的时限。把“控制台正在处理另一个挑战时，其他挑战可能自动接续”作为用户需认可的产品规则，并在队列显示剩余等待与预计自动动作，避免不可见的自动操作。

验收增加两个前台标签抢 reserve、优先窗口展示页关闭后其他页接替、两个账号同时准备而当前账号人工占用、队列中用户点开挑战临界点等场景。

## PR-R1-005 — P2：QR 入口仍有现存链接、文案和弹窗冲突，方案缺少明确迁移契约

位置：方案 §1 R07、§4、§11 第 205 行、§14 S4。

现有 `apps/api/src/xianyu-qr-login.ts:332` 的 QR 公共响应返回 `verificationUrl` 和 `verificationAutoLaunch`；`apps/web/src/features/accounts/qr-login/components/QrLoginView.tsx:30` 渲染“在新窗口打开验证链接”，下一行提示“验证页已由浏览器打开”。`QrLoginModal.tsx` 自己已有 aria-modal 弹窗。新方案只定义新增 verification API 不返回 URL，未写现有 QR 返回字段和旧 UI 的迁移行为，也未定义全局抽屉与现有扫码弹窗的焦点、层级和关闭语义。若仅接入 Coordinator 而沿用旧 UI，用户仍会被导向不同浏览器会话，或抽屉已准备却被扫码弹窗遮挡，错误启动 5 秒。

建议明确启用特性时 QR 旧验证链接不展示/不返回，新 UI 以 coordinator session reference 关联；兼容和回退路径分别写清。扫码弹窗转入同一挑战容器或被挂起，只有实际顶层可操作画面才 ACK；关闭挑战是否取消 QR、关闭扫码弹窗是否结束登录，需要一张明确操作表。现有 `verificationAutoLaunch` 的继续轮询语义需要与新字段兼容，避免去掉字段后把 verification_required 当终态而不再观察登录结果。

验收新增 QR 弹窗已打开时挑战出现、挑战关闭后扫码是否继续、重新打开、QR 过期、旧字段兼容以及旧“新窗口验证链接”不再出现。

## PR-R1-006 — P2：失败后的“我来重试”到底保证人工还是再次自动，接口和状态机未定义

位置：方案 §4 第 83 行；§9 第 177 行；§12 第 211–213 行；§15 第 2 条。

失败 UI 给“我来重试”，但 retry 只定义 subject 和复用活动会话，没有 `mode` 或人工意图。§12 说显式人工重试“可打开新的人工窗口”，未明确是新的 5 秒机会还是立即取得 90 秒控制；若原会话仍处 auto_active，是复用后预约还是返回错误也不清楚。更极端地，自动熔断已触发、用户点“我来重试”后短暂切后台，是否会再次触发自动或直接终结，没有一致产品承诺。按钮名应代表稳定行为。

建议定义显式人工重试意图的服务端字段/动作：有未终结会话按其安全边界预约或恢复；终态会话创建人工优先任务并由新鲜画面确认后授予控制；自动预算耗尽时明确保持等待人工，不能用展示超时偷偷转自动。取消/关闭/未确认的结果及人工时限起点都需列出。用户对同一按钮连点必须幂等，不能新建多个会话或重复授予 90 秒。

验收新增：手动失败重试、自动失败重试、handoff 失败重试、熔断下重试、活动会话重试、重复点击/断线重放；断言人工意图、预算、deadline 与界面文案一致。

## 可保留的设计决定

- 5 秒从真实画面和输入通道就绪后由服务端决定起点，客户端只显示倒计时；超时竞争在服务端仲裁。
- 90 秒固定人工窗口、3 秒断线宽限、控制 epoch 与输入释放屏障；刷新不额外赠送优先窗口。
- 原浏览器原会话的受限画面和指针操作，权限显式使用有效 manage scope。
- code=0 与账号恢复分开；身份/CAS/来源核销/IM 心跳继续作为业务成功依据。
- 原写操作不自动重放、总期限和自动预算持久化、首期单 owner、先技术验证再灰度。

以上表示设计方向可保留，不表示相关能力已实现或已通过测试。
