# 复杂前后端项目开发流程与规范

## 1. 文档定位

本文用于指导中大型后端、全栈、平台型项目的需求、设计、开发、联调、测试、发布与交接。

适用范围：

- 需要数据库、API、鉴权、消息、缓存、文件存储或第三方服务的项目；
- 需要前端页面、组件、状态管理、实时通信或高保真设计还原的项目；
- 需要多人协作、分阶段交付、可回滚和可审计的项目。

不适用于一次性脚本、单接口小改动、纯文案变更或纯配置调整。即使属于例外，也必须保留适用的最小验证证据。

---

## 2. 不可妥协的总规则

### 2.1 严格串行，门禁决定能否前进

项目按阶段推进。当前阶段未通过门禁，不得开始下一阶段的设计、编码、联调或部署。

阶段状态只有以下三种：

- PASS：所有适用门禁通过，所有必需评审通过，可以进入下一阶段；
- FAIL：存在可修复问题，停留在当前阶段，修复后重新验证；
- BLOCKED：存在 P0/P1 问题、关键权限未验证、数据破坏风险、不可复现构建或外部依赖阻塞，必须先清除阻塞。

“部分完成”“大部分通过”“后续补齐”都不能替代 PASS。

### 2.2 每阶段至少两轮独立评审

每个阶段至少进行两轮独立评审；默认进行三轮：

1. 业务 / 验收评审：目标、流程、边界、用户可见行为和验收标准；
2. 架构 / 数据流评审：模块边界、依赖方向、数据流、接口、状态和一致性；
3. 质量 / 安全 / 运维评审：测试、权限、安全、性能、日志、监控、发布和回滚。

低风险阶段可以只做两轮，但必须在评审记录中写明省略第三轮的理由和替代检查。

### 2.3 评审问题必须先修复，再送审

这是强制规则：

1. 每轮评审都必须登记问题、级别、证据、责任人和修复期限；
2. 当前轮评审存在未关闭问题时，不得把该阶段送入下一轮评审，也不得进入下一阶段；
3. 修复后，必须重新执行受影响的门禁项、测试和验证；
4. 重新验证通过后，才允许提交复审；
5. 复审必须确认问题已关闭，且没有引入新的回归；
6. 任一必需评审未通过，阶段仍为 FAIL 或 BLOCKED；
7. 连续两轮修复仍失败时，停止继续编码，升级为风险或决策项，明确需要的用户决策或外部依赖。

禁止使用以下方式“过审”：

- 先送审、再补问题；
- 将问题标记为“后续处理”“暂时忽略”；
- 降低测试范围、删除测试、关闭校验或修改测试让结果变绿；
- 只修复表面现象，不重新验证受影响链路；
- 以 mock、页面可打开或 HTTP 200 代替真实业务验收。

### 2.4 先证据，后结论

任何“已完成”“已修复”“可发布”的结论，必须由可复核证据支持：

- 变更文件和关键 diff；
- 构建、格式化、静态检查和测试命令；
- 测试输出、覆盖范围和失败记录；
- API 请求与响应；
- 数据库迁移、状态变化和回滚结果；
- 前端目标 viewport 截图、录屏或视觉回归对比；
- 部署演练、健康检查、回滚演练和监控告警结果。

无法执行的验证必须标记为“部分验证”或“被阻塞”，不得表述为整体完成。

### 2.5 小步纵向切片交付

每次只实现一个可运行的纵向切片，至少覆盖其所需的数据库、API、前端、测试和文档。禁止一次性生成整个项目后再统一验证。

### 2.6 保持可回退

每阶段完成后必须更新状态、决策、风险和回滚方式。修复失败时，优先回退到最近一次通过门禁的状态，而不是继续叠加未经验证的改动。

## 3. 角色与职责

| 角色 | 主要职责 |
| --- | --- |
| 产品 / 业务负责人 | 明确目标、范围、非目标、业务规则、验收标准和优先级 |
| 架构负责人 | 定义系统边界、模块职责、依赖方向、技术决策和演进路线 |
| 后端负责人 | 负责领域逻辑、数据模型、API、事务、事件、任务和可观测性 |
| 前端负责人 | 负责信息架构、页面、组件、状态、交互、响应式和高保真还原 |
| 设计负责人 | 提供高保真稿、设计标注、设计 token、资源和设计版本；参与视觉验收 |
| 测试 / QA | 定义测试层级、验收场景、回归范围和证据标准，独立执行评审 |
| 安全 / 运维负责人 | 负责鉴权、密钥、日志脱敏、性能、监控、发布、备份和回滚 |
| 评审人 | 独立检查当前阶段，不直接替代实现者确认自己的结果 |
| 项目负责人 | 维护门禁、状态、风险、评审记录和推进节奏 |

关键阶段应安排未参与主要实现的人进行独立复核。

## 4. 项目文档与记录

建议在项目根目录维护以下文档；已有同类文档时应复用，不要重复创建：

- docs/00-scope.md：目标、范围、非目标、成功标准、术语；
- docs/01-architecture.md：前后端与部署架构、模块边界、技术决策；
- docs/02-data-api.md：数据模型、迁移、API、事件、错误码、鉴权；
- docs/03-frontend-design.md：页面、路由、组件、状态、数据流和设计还原；
- docs/04-plan.md：依赖图、纵向切片、Definition of Done；
- docs/05-review-log.md：评审意见、修复、复核和结论；
- docs/06-risk-register.md：风险、影响、概率、缓解、负责人和截止时间；
- docs/07-visual-acceptance.md：视觉对比、偏差、豁免和复核结果；
- STATUS.md：当前阶段、门禁状态、阻塞项和下一步。

### 4.1 状态文件最小字段

项目阶段：0-8
阶段状态：PASS | FAIL | BLOCKED
最近一次通过门禁：编号 / 日期
当前目标：本轮唯一目标
已完成范围：可验证描述
未完成范围：明确列出
未解决风险：风险编号、级别、负责人
待复审问题：问题编号，无则写“无”
下一步：仅在 PASS 时填写

## 6. 各阶段流程与硬性门禁

### 阶段 0：项目启动与范围锁定

工作内容：

- 明确用户、业务目标、核心流程、非目标、成功标准和术语；
- 列出角色、权限、状态、外部依赖、合规要求和环境约束；
- 识别已有代码、框架、数据库、部署环境和团队约定；
- 建立“需求 → 验收标准 → 测试证据”的追踪关系；
- 明确高保真设计是否存在、设计来源、版本和使用范围。

门禁 0：

- 每个核心需求都有可验证的验收标准；
- 非目标和暂不实现内容已明确；
- 角色、权限和状态流转没有未标记歧义；
- 技术栈、环境和外部依赖已确认或明确列为假设；
- 设计输入已取得，缺失项已列为阻塞或假设；
- P0 阻塞问题为 0。

评审：业务评审、可实现性评审、异常场景评审。

门禁失败时，只能补充范围、假设和验收标准，禁止开始架构设计或编码。

### 阶段 1：系统架构与模块边界

工作内容：

- 设计后端分层、领域模块、服务边界、依赖方向和数据所有权；
- 设计前端路由、页面层、业务模块层、组件层和数据访问层；
- 明确同步调用、异步事件、缓存、队列、文件存储和第三方服务；
- 说明本地、测试、预发布和生产环境拓扑；
- 记录关键技术决策、替代方案、风险和 ADR。

门禁 1：

- 每个需求都映射到明确模块；
- 模块职责、输入、输出和依赖方向清晰；
- 数据所有权和跨模块访问方式已定义；
- 前端、后端、数据库和基础设施没有循环依赖；
- 安全、性能、可用性和可观测性均有落点；
- 页面、组件和 API 不依赖未定义的后端字段；
- 高风险决策都有 ADR 或等价记录。

评审：架构评审、数据流评审、运维安全评审。

门禁失败时，不得编写业务代码，只允许修订架构和决策记录。

### 阶段 2：数据模型、API 契约与安全边界

工作内容：

- 设计实体、关系、索引、唯一约束、审计字段、软删除和迁移策略；
- 定义 API 请求、响应、错误码、分页、排序、版本和兼容策略；
- 定义认证、授权、租户隔离、幂等性、事务边界和并发策略；
- 定义领域事件、消息格式、重试、去重和失败补偿；
- 为前端提供稳定的 API 契约或 OpenAPI 文档。

门禁 2：

- 所有核心用例都有数据模型和 API 映射；
- 字段类型、空值、默认值、唯一性、权限和生命周期已确定；
- 迁移可重复执行，或具备可靠回滚策略；
- 错误结构、鉴权失败行为和幂等策略统一；
- 敏感数据、日志脱敏、数据保留和访问审计已定义；
- 前端不直接依赖平台原始字段或内部数据库结构；
- 没有关键契约歧义。

评审：API 评审、数据完整性评审、安全隐私评审。

门禁失败时，不得同时推进前端联调或大规模后端实现。

### 阶段 3：前端信息架构、模块、组件与数据流

只要项目存在前端、管理台或其他调用方，本阶段就是强制阶段。

工作内容：

- 定义页面、路由、布局、导航层级和用户旅程；
- 将页面拆为业务模块、功能模块和可复用组件，明确职责、输入、输出和状态；
- 建立基础组件、表单、表格、弹窗、反馈、空状态、错误状态和加载状态清单；
- 定义服务端状态、缓存状态、全局状态、页面状态和临时表单状态的归属；
- 画出“用户操作 → 组件事件 → 状态更新 → API → 响应 → UI 更新”数据流；
- 定义请求生命周期、重试、取消、乐观更新、缓存失效和错误恢复；
- 定义响应式、可访问性、权限显隐和国际化要求；
- 将每个前端数据需求映射到阶段 2 的 API；
- 建立“高保真页面 / 状态 → 实现页面 / 组件 / 路由”的一一映射表。

门禁 3：

- 每个核心用户旅程都有页面、路由、组件和 API 映射；
- 每个页面都定义加载、成功、空数据、失败、无权限、禁用和提交中状态；
- 组件边界、复用范围和状态归属清晰，没有万能组件或隐式全局状态；
- 关键数据流可以追踪到 API、权限和数据库；
- 页面权限与后端强制鉴权一致；
- 高保真稿中的页面、组件、交互和状态都有实现计划；
- 前端设计不依赖未定义字段、接口或状态。

评审：用户流程评审、模块 / 组件评审、数据流评审。

门禁失败时，不得开始大规模页面开发，只允许完善设计或回退修订 API。

### 阶段 4：迭代计划与纵向切片编排

工作内容：

- 把需求拆为可独立运行的纵向切片，每个切片覆盖必要的数据库、API、前端、测试和文档；
- 建立任务依赖图，标注阻塞关系、风险和复杂度；
- 为每个切片定义 Definition of Done、测试范围、回滚方式和验收证据；
- 优先安排高风险、强依赖和能早期反馈的任务；
- 为视觉高保真还原安排独立视觉验收任务，而不是只写“页面完成”。

门禁 4：

- 所有切片都有目标、输入、输出、依赖和验收标准；
- 第一个切片可在当前环境运行，或有明确的环境准备任务；
- 高风险事项有提前验证任务；
- 单个切片不会同时引入多个未经验证的架构变化；
- 计划、风险、状态、评审和门禁记录位置已确定；
- 每个前端切片都有设计稿版本、目标 viewport 和视觉验收证据要求。

评审：计划完整性评审、风险评审、交付节奏评审。

### 阶段 5：单切片实现、测试与评审

每个切片都必须按以下顺序执行：

1. 读取上下文、已有代码、设计稿和测试；
2. 声明本次目标、输入、输出、禁止范围、假设和验收标准；
3. 实现最小可运行链路；
4. 补充边界、权限、错误处理和可观测性；
5. 编写或更新单元、集成、端到端和视觉验证；
6. 运行格式化、静态检查、构建和测试；
7. 执行切片门禁；
8. 进行至少两轮独立评审；
9. 修复评审问题，重新验证受影响范围，再送复审；
10. 更新状态、评审记录、风险记录和设计文档；
11. 按阶段 5.5 要求完成 Git 提交并记录提交哈希；
12. 只有 Git 门禁通过后，才允许进入阶段 6。

切片门禁：

- 满足验收标准，没有计划外行为变化；
- 后端、数据库、前端和 API 契约一致；
- 正常、失败、未登录、无权限、空数据、重复请求和关键并发场景有测试，或有书面豁免理由；
- 没有编译错误、静态检查错误、明显日志泄露或未处理异常；
- 迁移、配置、文档和回滚说明已同步；
- 构建、静态检查和测试命令已在当前环境真实执行并通过；
- 前端页面按设计稿实现，关键 viewport 的截图或视觉回归通过；
- 设计稿中的加载、空态、错误、禁用、弹窗、抽屉、hover、focus 等适用状态已覆盖；
- 真实或代表性数据下没有溢出、布局崩坏、字段缺失或错误提示不一致。

切片评审：功能评审、设计评审、质量评审。低风险切片也不得少于两轮。

### 阶段 5.5：Git 提交与版本门禁

本阶段是阶段 5 与阶段 6 之间的强制版本门禁。切片只有在评审问题完成“修复 → 重新验证 → 复审”并形成符合中文 Conventional Commits 规范的可追溯原子提交后，才能进入前后端集成。

门禁要求：

- 提交格式、提交范围、提交内容和提交历史可追溯；
- 提交说明使用中文，符合 `<type>(<scope>): <中文摘要>`；
- `git diff --check`、格式化、静态检查、构建和适用测试全部通过；
- 工作区不存在未经说明的未提交修改；
- 不得包含密钥、敏感数据、临时代码、生成物或无关改动；
- 提交哈希、验证命令和评审结果已记录；
- 门禁失败时状态为 `FAIL`；发现泄密、不可回滚或不可追溯提交时状态为 `BLOCKED`。

Git 门禁通过后，才允许进入阶段 6。

### 阶段 6：前后端集成与端到端验证

验证真实 API、鉴权、错误响应、分页、缓存、状态刷新、跨域、上传、时区、编码、重试、超时和网络失败。检查前端权限显隐与后端强制鉴权一致，并验证迁移、种子数据和测试数据清理。

门禁 6：

- 核心用户旅程可从真实入口走到持久化结果；
- 前后端契约、错误码、权限和状态流转一致；
- 异常路径可恢复，不产生脏数据、重复提交或敏感信息泄露；
- 集成、端到端和回归测试通过；
- 设计稿覆盖的核心页面在目标尺寸下通过视觉验收；
- 真实数据、长文本、空数据、异常数据和权限差异下页面仍可用；
- WebSocket、轮询或重连后的 UI 状态与服务端状态一致。

评审：用户旅程评审、集成故障评审、回归评审。

### 阶段 7：安全、性能、可观测性与发布准备

工作内容：

- 执行依赖漏洞、鉴权、越权、注入、密钥、敏感日志和输入校验检查；
- 检查延迟、吞吐、索引、缓存、并发和资源使用；
- 完善结构化日志、指标、追踪、健康检查和告警；
- 定义备份、恢复、迁移、灰度、限流、熔断和回滚策略；
- 验证前端错误监控、关键交互埋点和视觉回归基线。

门禁 7：

- 没有未接受的高危安全问题；
- 关键接口达到约定性能 / 容量目标，或已记录偏差和后续计划；
- 生产密钥、配置、监控和告警已核对；
- 迁移、备份、恢复和回滚已验证，或有明确可接受替代方案；
- 关键页面的视觉基线、断点和浏览器范围已确定；
- 重大视觉偏差、交互缺失或可访问性问题已修复或获得书面豁免。

评审：安全评审、性能与成本评审、运维与可观测性评审。

### 阶段 8：发布、回滚与交接

工作内容：

- 生成部署说明、环境变量清单、迁移顺序、启动命令和健康检查；
- 执行可复现的构建和部署演练；
- 验证回滚、数据兼容性和发布后冒烟；
- 交接 API、架构决策、已知限制、风险、监控和后续计划；
- 交接前端设计版本、视觉基线、已批准偏差和未完成还原项。

门禁 8：

- 新环境可按文档部署；
- 发布后核心冒烟测试通过；
- 回滚路径已验证，或有明确替代方案；
- 交接文档完整，剩余风险有负责人和下一步；
- 发布版本与设计稿版本、API 版本和数据库迁移版本可追踪；
- 不存在未披露的关键视觉、交互、权限或数据一致性问题。

评审：发布就绪评审、文档交接评审、事故演练评审。

## 7. 前端设计与高保真还原规范

前端不是后端接口的展示层，而是独立的产品交付面。只要项目存在页面、管理台或调用方，设计和高保真还原就属于硬验收范围。

### 7.1 设计输入必须完整

开发前必须确认并记录：

- Figma 或高保真设计图的链接、版本和页面清单；
- 设计标注、字体、颜色、间距、圆角、阴影、边框和图标规范；
- 图片、视频、插画、图标、动效和空状态资源；
- 桌面、平板、移动端等断点和目标 viewport；
- hover、active、focus、loading、error、disabled、modal、drawer、toast 等交互说明；
- 设计缺失项、临时假设和需要产品决策的阻塞项。

缺少关键信息时，必须标记为假设或 BLOCKED，不得用“先按经验做”替代设计确认。

### 7.2 设计到实现必须可追踪

每个设计页面和关键状态都必须有以下映射：

设计稿页面 / 状态 → 路由 → 页面组件树 → 业务模块 → 状态归属 → API / 数据契约 → 验收证据

不允许用“相似页面”代替未映射页面，也不允许只实现默认成功态而忽略设计稿中的异常态。

### 7.3 统一 token，禁止视觉漂移

颜色、字号、行高、间距、圆角、阴影、边框、图标尺寸和断点必须抽取为设计 token 或主题变量。禁止在多个页面散落硬编码，导致同一元素在不同页面出现视觉漂移。

### 7.4 状态必须齐全

适用的状态至少包括：

- 首次加载、刷新、分页加载、提交中；
- 成功、空数据、失败、重试、超时、部分成功；
- 未登录、无权限、禁用、过期、冲突、重复提交；
- 长文本、大数据量、图片加载失败、断网、重连；
- 弹窗、抽屉、确认卡、表单校验和取消操作。

状态文案、按钮可用性、焦点位置和恢复路径必须与产品规则和后端契约一致。

### 7.5 视觉验收证据

每个高保真切片至少保留：

- 目标 viewport 的实现截图或录屏；
- 与设计稿的对比图或视觉回归结果；
- 页面、状态、浏览器和数据条件；
- 逐项偏差记录、严重级别、责任人和修复结果；
- 已批准豁免及其复核日期。

关键视觉偏差未修复、没有书面豁免或没有复核证据时，门禁必须 FAIL。

### 7.6 响应式、可访问性和真实数据

- 目标断点下不溢出、不遮挡、不出现不可操作控件；
- 键盘操作、焦点、语义标签、对比度和触控尺寸满足项目要求；
- 使用真实或代表性数据验证长短文本、图片、权限差异和异常数据；
- 不能只凭静态 mock、页面可打开或组件存在来宣称完成。

## 8. 测试与验证规范

### 8.1 测试层级

| 层级 | 目标 | 最低要求 |
| --- | --- | --- |
| 单元测试 | 验证纯业务规则、状态机、校验和转换 | 正常、边界、非法输入、关键异常 |
| 集成测试 | 验证模块、数据库、缓存、队列和外部适配 | 真实依赖或可控容器环境 |
| 端到端测试 | 验证真实用户入口到最终结果 | 真实前端入口、真实 API、测试数据和持久化结果 |
| 视觉回归 | 验证页面与高保真稿的一致性 | 固定 viewport、代表性数据、偏差记录 |
| 发布冒烟 | 验证部署后核心可用性 | 登录、核心读路径、关键写路径和健康检查 |

冒烟测试可以作为部署后的额外检查，但不能替代单元、集成、端到端或视觉测试。

### 8.2 变更与测试映射

- 修复缺陷：必须增加一个修复前失败、修复后通过的回归测试；
- 新增业务逻辑：覆盖正常、边界和非法输入；
- 修改持久化、传输、消息、缓存或服务装配：增加相应集成测试；
- 修改用户流程或公开 API：增加真实端到端测试；
- 修改高保真页面：增加视觉回归或目标 viewport 截图验收；
- 修改状态机：覆盖成功、非法转换、资源不存在、权限失败、重复请求、持久化失败和取消 / 重试。

### 8.3 推荐验证顺序

格式化 / lint → 类型检查 / 编译 → 受影响单元测试 → 受影响集成测试 → 端到端测试 → 视觉回归或截图比对 → 完整测试命令

若某一步无法执行，必须记录原因、影响范围和替代证据；不得静默跳过。

## 9. 纵向切片 Definition of Done

一个切片只有同时满足以下条件，才可标记完成：

- 需求、接口、数据、前端页面和测试范围已明确；
- 代码只覆盖本切片范围，没有计划外行为变化；
- 后端、数据库、前端和 API 契约一致；
- 正常、失败、未登录、无权限、空数据、重复请求和关键并发场景已验证；
- 必要的迁移、配置、日志、监控、文档和回滚说明已同步；
- 构建、静态检查、单元、集成、端到端和视觉验证已按适用范围真实执行；
- 至少两轮独立评审完成，所有评审问题已关闭并完成复核；
- STATUS、review-log、risk-register 和设计文档已更新；
- 未遗留未标注假设、关键文档缺口或不可接受风险。

## 10. 评审问题闭环协议

### 10.1 问题等级

| 等级 | 定义 | 处理要求 |
| --- | --- | --- |
| P0 | 数据破坏、越权、核心流程不可用、不可回滚 | 立即 BLOCKED，修复并复审后才能继续 |
| P1 | 核心验收失败、关键契约错误、无法复现构建 | 阶段 FAIL / BLOCKED，禁止进入下一步 |
| P2 | 非核心缺陷、明显设计偏差、重要可维护性问题 | 必须修复后才能关闭本轮评审 |
| P3 | 低风险改进建议 | 可记录为后续任务，但不能掩盖 P0-P2 |

### 10.2 问题状态

OPEN → FIXING → READY_FOR_REVIEW → VERIFIED → CLOSED

只有 VERIFIED 才能进入 CLOSED。修复者不能仅凭自述关闭问题，必须提供验证证据，并由评审人复核。

### 10.3 评审记录模板

评审轮次：R1 / R2 / R3 / 复审
评审类型：业务 / 架构数据流 / 质量安全运维 / 视觉
评审范围：阶段、切片、页面、接口或模块
结论：PASS / FAIL / BLOCKED

问题：问题描述
级别：P0 / P1 / P2 / P3
证据：文件、命令、截图、接口响应或日志
责任人：姓名或角色
修复：实际改动
复验：重新执行的门禁和测试
复审结论：OPEN / VERIFIED / CLOSED

### 10.4 复审前检查清单

- 所有问题都有唯一编号；
- 所有 P0-P2 问题都有修复记录；
- 受影响门禁已重新执行；
- 受影响测试、构建和视觉验收已重新执行；
- 没有使用 skip、only、todo、过滤测试或关闭校验规避失败；
- 复审人确认问题已关闭，没有回归；
- STATUS、review-log 和 risk-register 已同步。

## 11. 失败处理、例外与禁止推进

任一门禁项 FAIL，阶段状态必须为 FAIL，禁止进入下一阶段。

以下情况必须标记为 BLOCKED：

- 存在 P0/P1 问题；
- 关键权限、鉴权或数据隔离未验证；
- 存在数据破坏或不可逆迁移风险；
- 构建、测试或部署无法复现；
- 关键设计输入、外部服务或环境依赖缺失；
- 核心高保真页面缺失、严重偏差且没有批准豁免。

修复要求：

1. 只修改与失败项相关的范围；
2. 不借机扩大需求或重构无关模块；
3. 修复后重新执行受影响门禁和至少两轮独立评审；
4. 连续两轮修复仍失败时停止编码，更新风险记录并请求决策；
5. 禁止“先合并再说”“后续再处理”“暂时忽略”。

### 11.1 受控例外

极小脚本、一次性原型、生成代码、纯配置、纯文档或已有项目明确约定的场景，可以降低部分要求，但必须：

- 说明使用了哪一项例外；
- 保留仍然适用的最强验证；
- 不能把冒烟测试写成端到端测试；
- 不能让最终报告超出真实证据范围；
- 不能绕过安全、权限和数据完整性检查。

## 13. 项目完成定义

只有同时满足以下条件，才能宣称项目完成：

- 所有适用阶段门禁均为 PASS；
- 每个阶段至少完成两轮独立评审，关键阶段完成第三轮安全 / 运维评审；
- 核心功能、异常场景、权限、数据流和关键状态均有证据；
- 构建、静态检查、单元、集成、端到端、视觉回归和发布演练按适用范围完成；
- 前端页面、高保真设计还原、响应式、可访问性和关键交互完成验收；
- 没有未说明的高危问题、未标记假设、未关闭的 P0-P2 评审问题或关键文档缺口；
- STATUS.md 明确记录已完成范围、未完成范围、剩余风险和后续计划；
- 新环境可按文档部署，发布后可验证，回滚路径可执行或有可接受替代方案。

如果任一条件不满足，只能报告为“部分完成”或“被阻塞”，不得报告为“已完成”或“可上线”。

## 14. Git 提交规范与版本门禁

Git 提交是阶段 5 完成后的必经步骤，Git 门禁未通过，不得进入阶段 6 前后端集成，也不得合并或发布。

### 14.1 提交格式

所有提交必须遵循 Conventional Commits 规范，提交说明必须使用中文，类型关键字保留标准英文：

`<type>(<scope>): <中文摘要>`

允许的类型：

| 类型 | 用途 |
| --- | --- |
| feat | 新增功能 |
| fix | 修复缺陷 |
| docs | 文档或规范变更 |
| style | 仅格式、空格、排版，不改变逻辑 |
| refactor | 重构，不改变外部行为 |
| perf | 性能优化 |
| test | 新增或修改测试 |
| build | 构建、依赖或打包变更 |
| ci | CI/CD、自动化流水线变更 |
| chore | 其他工程维护 |
| revert | 回滚已有提交 |

要求：

- 摘要用中文动宾短句，首行建议不超过 72 个字符，不加句号；
- scope 使用模块、领域或切片名称；
- 破坏性变更在类型后增加 `!`，并在正文或脚注中写明 `BREAKING CHANGE:`；
- 复杂变更正文必须说明背景、方案、影响、验证命令和结果；
- 可使用 `Refs: #123`、`Closes: #123` 关联任务或缺陷。

示例：

```text
feat(订单): 新增订单取消流程
fix(鉴权): 修复令牌过期后的重试死循环
docs(流程): 增加 Git 提交与版本门禁规范
test(订单): 补充重复提交与无权限回归测试
```

评审问题修复应形成可追踪提交，例如：`fix(订单): 修复 R1-P1-003 权限校验问题`。

### 14.2 提交粒度与分支要求

- 一个提交只包含一个逻辑变更，不混合无关重构、格式化和业务修改；
- 提交必须包含必要的代码、测试、文档、迁移和配置变更；
- 不得提交密钥、密码、生产数据、临时文件、构建产物、调试日志或冲突标记；
- 禁止使用 `WIP`、`临时提交`、`修改若干问题`、`完成开发`、`update code` 等模糊说明；
- 开发分支命名应包含任务类型和任务编号，例如 `feature/123-order-cancel`、`fix/456-auth-retry`；
- 受保护分支禁止强制推送；个人分支改写历史时只能使用 `--force-with-lease`；
- 评审开始后，问题必须先修复并提交，再重新执行受影响验证并送复审；
- 不得通过删测试、关校验、改测试或强推来掩盖未修复问题。

### 14.3 Git 提交门禁

提交前必须真实执行：

```bash
git status --short
git diff --check
git diff --stat
```

并按项目适用范围执行格式化、lint、类型检查、构建、单元测试、集成测试、端到端测试和视觉回归。

门禁通过条件：

- 提交格式符合 Conventional Commits，摘要和正文使用中文；
- 提交范围只覆盖当前切片或当前修复问题；
- 工作区不存在未经说明的未提交修改；
- 不存在密钥、敏感数据、临时文件、调试代码或冲突标记；
- `git diff --check` 通过；
- 适用的构建、静态检查和测试命令全部通过；
- 评审问题已经完成“修复 → 重新验证 → 复审”闭环；
- 提交哈希、验证命令、评审轮次和结果已记录到 `STATUS.md`、`review-log` 或阶段交付报告；
- 最终提交能够独立回滚，不依赖未提交的本地文件。

任一条件不满足，阶段状态必须为 `FAIL`；发现密钥泄露、错误提交到受保护分支、不可回滚变更或提交内容无法追溯时，状态必须为 `BLOCKED`。

提交本身不能替代评审复核。只有在提交后重新执行受影响验证并由评审人确认问题关闭，才允许进入下一阶段。
